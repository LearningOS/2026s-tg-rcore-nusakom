# AI 协作方法论

## 核心原则

> AI 是学习的加速器，不是学习的替代品。

在 OS 内核开发中使用 AI 工具的核心原则：

1. **理解优先**：先理解原理，再让 AI 帮助实现
2. **验证思考**：用 AI 验证自己的思路，而非直接要答案
3. **记录过程**：将 AI 协作过程记录在周日志中，形成可复用的知识

---

## 协作策略

### 策略 1：分层提问

将复杂问题分解为多个层次，逐步深入：

```
层次 1（概念）：
  "什么是 Sv39 三级页表？虚拟地址是如何翻译为物理地址的？"

层次 2（框架）：
  "在 tg-rcore-tutorial 框架中，AddressSpace::translate() 的作用是什么？
   它的参数和返回值分别是什么？"

层次 3（实现）：
  "在 ch4 的 sys_trace 实现中，如何用 translate() 检查用户地址的读权限？
   如果地址不可读，应该返回什么？"
```

### 策略 2：提供充分上下文

AI 的回答质量取决于上下文的完整性：

```
❌ 差的提问：
  "mmap 怎么实现？"

✅ 好的提问：
  "在 tg-rcore-tutorial-ch4 中，我需要实现 mmap 系统调用（syscall ID 222）。
   框架使用 AddressSpace::map() 进行页表映射，页表标志位格式为 'U[X][W][R]V'。
   Linux mmap 的 prot 参数中 PROT_READ=1, PROT_WRITE=2, PROT_EXEC=4。
   请帮我写出 prot 到标志位字符串的映射代码，并解释每一位的对应关系。"
```

### 策略 3：代码审查模式

实现完成后，让 AI 进行代码审查：

```
"以下是我实现的 stride 调度算法的 fetch() 方法：
[粘贴代码]

请检查：
1. 是否正确处理了 stride 溢出？
2. 线性扫描的时间复杂度是否满足要求？
3. 是否有边界条件遗漏（如空队列）？"
```

### 策略 4：错误诊断

遇到编译错误或测例失败时：

```
"以下代码编译报错：
[错误信息]

相关代码：
[代码片段]

我认为问题可能是 [你的分析]，请帮我确认并给出修复方案。"
```

## OS 内核开发场景下的 AI 优势与局限

### 优势

| 场景 | AI 的帮助 |
|------|-----------|
| 理解框架 API | 快速解释 `translate()`、`map()`、`unmap()` 等 API 的语义 |
| 算法实现 | 将银行家算法的伪代码转化为 Rust 实现 |
| 调试 unsafe 代码 | 分析裸指针操作的安全性 |
| 位操作 | 解释 prot 位顺序、页表标志位格式等 |
| 生命周期问题 | 分析 Rust 借用检查器的错误 |

### 局限

| 场景 | 局限说明 |
|------|----------|
| 运行时行为 | AI 无法在 QEMU 中实际运行代码，无法观察运行时状态 |
| 框架内部实现 | 对 tg-rcore-tutorial 框架的内部实现了解有限，可能给出不准确的建议 |
| 性能优化 | 内核性能优化需要实际测量，AI 只能给出理论建议 |
| 硬件行为 | RISC-V 硬件的具体行为（如 TLB 刷新时机）需要查阅规范 |

## 学习效果对比

使用 AI 辅助学习 OS 内核的效果：

- **速度**：完成 5 个章节的实现约需 1 周，传统方式可能需要 3-4 周
- **深度**：通过与 AI 的对话，对每个概念的理解更深入（可以反复追问）
- **广度**：AI 能快速介绍相关背景知识（如 Linux 的 mmap 语义、POSIX 标准）
- **代码质量**：AI 辅助的代码审查减少了低级错误

关键是：AI 加速了**实现**过程，但**理解**仍需要自己完成。
